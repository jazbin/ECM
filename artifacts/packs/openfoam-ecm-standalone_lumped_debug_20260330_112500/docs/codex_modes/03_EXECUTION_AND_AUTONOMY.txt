MODE: Execution and Autonomy

3) Autonomy Protocol (when you would normally ask questions)
Primary rule: do not stop for routine clarifications; apply this protocol.

A) Missing/ambiguous information decision tree
1) Identify what is missing (units, file paths, defaults, acceptance criteria).
2) Search locally:
   - rg/find across docs/, CONTRACTS/, RUNBOOK/, TASKS/, PLANS/
   - check provided PDFs/requirements in docs/
3) Choose the least-committing default consistent with repository contracts:
   - prefer dictionary/config-driven behavior over hard-coding
   - prefer feature flags / reversible changes
   - preserve IO contracts unless explicitly updating them
4) Log the assumption:
   - decision log (date + rationale)
   - assumptions register (a single global list)
5) Proceed with a bounded implementation and a verification step that would fail
   if the assumption is wrong.
6) Escalate only if truly blocked (see Escalation Protocol).

8) Change Discipline (code + config + docs)
1) Make bounded changes:
   - small surface area
   - reversible where possible
2) Preserve contracts:
   - schema, units, IO formats, naming conventions
3) Do not "silently change behavior":
   - every behavior change requires a verification step
4) Prefer feature flags over hard behavior switches when uncertain.
5) Do not use "..." placeholders inside files; keep file edits complete.
6) Maintain repo conventions (formatting, naming, directory layout).

13) Defaults When Information Is Missing
Use safe defaults that minimize unintended behavior changes:
- maintain unit consistency; do not introduce unit ambiguity
- prefer conservative parameter priors (do not overclaim performance)
- default to autonomy-safe behavior: feature flags off, no surprises
- prefer robust IO: explicit keys/IDs, atomic writes, schema validation

4) Execution Lanes and Approval-Gated Actions
Use two execution lanes to control risk/cost.

Lane A -- Unattended / fast / safe (default)
- lightweight commands, static checks, quick builds, short smoke runs
- actions that do not modify external systems or consume significant compute
- can run without interactive approval once repo policy allows

Lane B -- Interactive / expensive / high-risk
- long CFD runs, large downloads, risky environment changes, destructive ops
- requires explicit authorization recorded in decision log (or repo ledger)
- enter Lane B only after Lane A passes, and only with rationale + budget

If approvals block a required action:
- record the situation, provide a fallback plan, and ask the user for approval.
